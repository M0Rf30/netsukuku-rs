| `2010-lopumo-scalable-mesh-networks-address-space-balancing.pdf` | Scalable Mesh Networks and The Address Space Balancing Problem | Andrea Lo Pumo | 2010 (declared June 8 2010; archive.org publication date 2010-05-31) | University of Cambridge Computer Laboratory, Girton College — **MPhil dissertation** (not PhD; "Master of Philosophy in Advanced Computer Science"), supervisor Jon Crowcroft, 2nd reader Eiko Yoneki | **FULL TEXT** | **THE** formal academic treatment. 14,783 words, 67 pages (per archive.org OCR metadata), 6 chapters. Formalizes the gnode/level hierarchical addressing model abstractly (not Netsukuku-specific — generalizes to any bounded-size-*S*, *L*-level hierarchy), proves NP-hardness-adjacent results, defines the **address-space-balancing problem** precisely (Prop 3.2.1: a network can be saturated with only `(S-1)L+1` nodes despite having free capacity elsewhere), proves only two fix strategies exist (node migration vs. gnode emptying — Prop 3.2.2), introduces **virtual nodes/virtual links** as the workaround for cases with no valid re-addressing (Def 3.4.3), and specifies two concrete balancing rules — **Preemptive Balancing (PB-rule)** and **Last-Minute (LM-rule)** — with correctness proofs and simulated cost bounds: worst-case address changes are `O(√N)`, but under constant churn, reconfigurations grow at least linearly in N. **This is the rigorous foundation an implementer needs before writing any Rust gnode-hooking/rebalancing code** — the Vala `hooking` module almost certainly implements one of these two rules; identify which, and validate against the proofs here. |

## Open questions / risks for the Rust port

- **Which balancing rule does the Vala `hooking` module actually implement — PB-rule or LM-rule (or neither)?** The thesis proves both are correct but have different migration-count/overhead tradeoffs (LM-rule triggers only when a group is already full; PB-rule triggers pre-emptively on every join/leave). This must be resolved by reading `research/impl/vala/hooking` against thesis §3.5 before writing the Rust gnode-rebalancing logic — implementing the wrong rule, or an ad-hoc third rule, would silently diverge from the only rigorously-proven-correct design.
- The thesis's hierarchical model (`Definition 2.2.1`) is *more general* than what any Netsukuku implementation actually uses: it allows `L` levels of *any* bounded size `S`, whereas Netsukuku fixes `S=256` (1 byte per level) for IPv4 and uses a different fixed scheme for IPv6 (see 01-vala-core-routing.md for the concrete `gsize`/`levels` constants). When implementing, keep the *general* algorithm parametric (matching the thesis) rather than hard-coding 256, since the Rust port may want configurable group sizes for testing at small scale.
- The 2009 website editions of qspn.pdf/topology.pdf/andna.pdf have **not been diffed against their 2007 arXiv counterparts**. If the Rust port needs to resolve an ambiguity in the arXiv QSPN text, cross-check the 2009 website edition first (it's 2 years later and is the version actually linked as canonical from the main site doc) before assuming the arXiv preprint is final.
- Four NTK_RFCs (0011 Carciofo, 0012 Net Split, 0013 Caustic Routing, and the unnumbered Viphilama Static) describe features **with no implementation in any retrieved source tree** (Vala or C). These should be treated as explicitly out-of-scope / stretch-goal for an MVP Rust port unless the user asks for them — implementing an unimplemented, self-described-incomplete paper spec from scratch is a major undertaking with no reference behavior to test against.
- NTK RFC 0014 (P2P over Netsukuku, the generic DHT layer) states ANDNA is implementable as two instances of this generic P2P/DHT service. Confirm with the ANDNA-focused note (02-vala-services-daemon.md) whether the actual Vala `andna` module was built as a special-case implementation or genuinely layers on a shared P2P/DHT primitive — this affects whether the Rust port should build a generic DHT trait/module that ANDNA (and any future P2P service) consumes, versus a monolithic ANDNA-only implementation.
- No independent (non-author) peer review of QSPN's core correctness claims (loop-freedom, convergence time bounds) was found anywhere in the literature search. The Rust port cannot lean on third-party validation of QSPN's algorithmic correctness — any correctness bugs found during implementation are *original* findings, not confirmable against a prior independent analysis.
- The two thesis PDF copies (archive.org vs. author's dyne.org upload) were not byte-diffed beyond the first ~500 lines of extracted text; if the port ever needs to cite a specific page/line number from the thesis, re-verify against both copies since pagination could differ between the two PDF exports despite matching content in the portions inspected.
